## 2. Нагрузка при 60 клиентах

### Запросов в минуту

| Тип | 1 клиент/мин | 60 клиентов/мин |
|-----|-------------|----------------|
| Батч событий (каждые 10 сек) | 6 | **360** |
| Heartbeat | 1 | 60 |
| Активность | 1 | 60 |
| История браузера | 1 | 60 |
| Pending flush (retry) | 1 | 60 |
| Скриншоты | 0.2 | 12 |
| Политики | 0.2 | 12 |
| Логи клиента | 0.2 | 12 |
| Листинг директорий | 0.1 | 6 |
| **Итого** | **~11** | **~642 req/min** |

**= примерно 11 запросов в секунду на весь сервер**

### Трафик

| Направление | Объём |
|-------------|-------|
| Скриншоты | ~28 MB/час = 672 MB/день = **~20 GB/месяц** |
| Остальные данные | ~1–1.5 MB/мин = **~2 GB/месяц** |
| Итого трафик входящий | ~25 KB/сек при стабильной работе |

### Записей в PostgreSQL в минуту (60 клиентов)

| Таблица | Writes/мин |
|---------|-----------|
| Heartbeat + Client (lastSeen) | ~120 |
| Activity + TimesheetDay | ~120 |
| Event (системные события) | ~300 |
| BrowserActivity | ~600 |
| Screenshot | ~12 |
| WorkSession / WorkSessionEvent | ~120 |
| **Итого** | **~1 250–1 500 writes/мин ≈ 20–25 writes/сек** |

## 3. Оценка: хорошо или плохо?

### ✅ Что хорошо

- **11 req/сек** — Node.js без проблем держит 500–1000+ req/сек; запас огромный
- **25 writes/сек** — PostgreSQL комфортно работает до 5 000+ writes/сек
- **60 WebSocket-соединений** — ничтожно мало, стандартный сервер держит тысячи
- **Трафик ~25 KB/сек** — для локальной сети (LAN) практически незаметно
- **Архитектура выдержит 200–300 клиентов** без изменений инфраструктуры

### ⚠️ Что плохо

#### Проблема 1 — Холостые запросы событий (главная)

Таймер `_eventBatchTimer` в `DataTransmissionService` стреляет **каждые 10 секунд всегда** — даже если очередь событий пустая. При 60 клиентах это **360 бесполезных HTTP-запросов в минуту**, каждый из которых:
- открывает соединение с сервером
- сервер его читает и расшифровывает
- обнаруживает что полезных данных нет
- закрывает соединение

Итог: ~52% всех запросов к серверу — холостые.

#### Проблема 2 — Нет jitter (синхронизированный старт)

Все таймеры стартуют с `TimeSpan.Zero` — то есть **немедленно при запуске службы**. Если утром в 08:00 включаются все 60 ПК одновременно:

```
08:00:00 → 60 heartbeat + 60 скриншота + 60 батчей событий = ~180 запросов за 1 секунду
08:01:00 → снова 60 heartbeat + 60 activity
08:02:00 → снова...
```

Клиенты остаются синхронизированными навсегда, создавая пиковую нагрузку каждую минуту вместо равномерной.

#### Проблема 3 — Дисковое пространство под скриншоты

```
60 клиентов × 12 скриншотов/час × 400 KB = 28 MB/час
                                           = 680 MB/день
                                           = ~20 GB/месяц (при retention 30 дней)
```

При retention в 30 дней постоянный объём на диске ≈ **20 GB**. Нужен мониторинг свободного места.

#### Проблема 4 — Политики скачиваются каждые 5 минут без проверки изменений

`GET /api/policies/{id}` вызывается каждые 5 минут вне зависимости от того, менялись политики или нет. Лишняя нагрузка на сервер и трафик. Нужна проверка по хэшу или ETag.

## 4. Рекомендации по исправлению

### Фикс 1 — Не отправлять пустой батч событий

**Файл:** `client/Services/DataTransmissionService.cs` → метод `FlushEventBatchAsync`

```csharp
private async Task FlushEventBatchAsync()
{
    // Добавить эту проверку в самое начало:
    if (_eventQueue.IsEmpty) return; // не тратить ресурсы если нечего отправлять

    if (await _batchLock.WaitAsync(0))
    {
        // ... остальной код без изменений
    }
}
```

**Эффект:** устраняет ~360 холостых запросов в минуту при 60 клиентах (−52% от общего числа запросов)

---

### Фикс 2 — Добавить jitter к таймерам

**Файл:** `client/ProctorWorker.cs` → метод `ExecuteAsync`

```csharp
protected override async Task ExecuteAsync(CancellationToken stoppingToken)
{
    // Случайный сдвиг при старте чтобы клиенты не синхронизировались
    var rnd = Random.Shared;
    var jitter = TimeSpan.FromSeconds(rnd.Next(0, 30));

    var screenshotLoop = RunScreenshotLoop(stoppingToken);

    // Heartbeat: старт через jitter, потом адаптивно
    _heartbeatTimer = new Timer(async _ => await SendHeartbeat(), null,
        jitter, Timeout.InfiniteTimeSpan);

    // Активность: старт через jitter, потом каждую минуту
    _activityReportTimer = new Timer(async _ => await SendActivitySnapshot(), null,
        jitter, TimeSpan.FromMinutes(1));

    // Политики: старт через jitter + смещение
    var policyInterval = _settings.PolicyUpdateIntervalMs > 1000 ? _settings.PolicyUpdateIntervalMs : 60000;
    var policyUpdateTimer = new Timer(async _ => await UpdatePolicies(), null,
        jitter + TimeSpan.FromSeconds(15), TimeSpan.FromMilliseconds(policyInterval));
    // ...
}
```

**Эффект:** 60 клиентов запускаются в разное время (разброс до 30 секунд), пиковая нагрузка распределяется равномерно

---

### Фикс 3 — Кэшировать политики по хэшу

**Файл:** `client/Services/PolicyService.cs`

Сохранять хэш последней загруженной политики и не перезагружать если хэш на сервере не изменился. Сервер должен возвращать `304 Not Modified` при совпадении ETag.

**Эффект:** устраняет ~12 лишних запросов/мин при 60 клиентах (−2% нагрузки, плюс меньше дешифровки)

## 5. Итог — приоритеты

| Приоритет | Фикс | Сложность | Эффект |
|-----------|------|-----------|--------|
| 🔴 Высокий | Пропускать пустой батч событий | Trivial (1 строка) | −52% холостых запросов |
| 🟡 Средний | Jitter к таймерам при старте | Простой (5 строк) | Убирает пиковую нагрузку при синхронном включении |
| 🟢 Низкий | ETag / хэш для политик | Средний (клиент + сервер) | Незначительный |

### Заключение

**При 60 клиентах система работает нормально.** Реальной проблемы производительности нет — запас по пропускной способности 10–20x. Единственный практический фикс, который стоит сделать прямо сейчас — **убрать холостые запросы батча событий** (1 строка кода). Остальное — оптимизация на будущее при росте до 300–500 клиентов.

Критический параметр для мониторинга: **свободное место на диске** (~20 GB занято скриншотами при 30-дневном retention на 60 клиентах).
